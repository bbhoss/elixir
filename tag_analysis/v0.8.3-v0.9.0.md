# Changes from v0.8.3 to v0.9.0

## Overview

**Release Date:** May 22-23, 2013
**Total Commits:** 42 commits
**Date Range:** May 22, 2013 to May 23, 2013

This minor version release focused on major architectural improvements to the Enum module, module naming conventions, and IEx interactive shell enhancements.

---

## Summary

v0.9.0 represents a significant step forward for Elixir with three major themes:

1. **Reducers Architecture**: A fundamental shift from the iterator-based approach to a reducers-based model in the Enum module, resulting in cleaner APIs and more efficient implementations. This was driven by the work of contributors like ericmj who recognized that reducers provide a more elegant and performant abstraction.

2. **Module Naming Standardization**: Changing how Elixir modules translate to Erlang atoms - from `Elixir-Module` to `Elixir.Module` notation. This change affects how modules are represented internally and likely simplifies interoperability with Erlang code while being more intuitive.

3. **Interactive Shell Configuration**: Introduction of `.iex` file support, allowing users to customize their IEx environment with startup code, imports, and bindings. This feature enhances the development experience by enabling reproducible shell configurations.

The release demonstrates a maturing platform making strategic architectural decisions to improve code quality and developer experience.

## Major Features and Improvements

### 1. Reducers-Based Enumeration (Breaking/Major Refactoring)

**Key Commits:**
- `66476b31d1` - Merge pull request #1102: Reducers
- `3f946d4af0` - Use reducers in Enum, File and URI
- `9318f747f4` - Add reduce to Enum.Iterator protocol
- `a1ec5f1552` - Clean up and fixes in reducer code

**What Changed:**
The Enum module underwent a major refactoring from an iterator-based design to a reducers-based model. This architectural change simplified the implementation significantly, with the Enum module being reduced by 514 lines of code (1138→429 insertions, 943 deletions) while maintaining the same public API. The reducers pattern provides better composability and performance for enumeration operations.

**Impact:**
- More efficient enumeration operations
- Cleaner, more maintainable code in the Enum module
- The change is largely internal and transparent to users, though it represents an important architectural improvement
- File and URI modules were also updated to use reducers

### 2. Module Naming Convention Change

**Key Commit:**
- `2c98c0999d` - An Elixir module now translates to `Elixir.Module` instead of `Elixir-Module`

**What Changed:**
Elixir modules now translate to atoms using dot notation (`Elixir.Module`) instead of hyphenated notation (`Elixir-Module`). This affects:
- How modules are represented internally in Erlang
- The compilation output and `.beam` file naming
- How modules appear when inspected or converted to atoms

For example:
- `Mix.Tasks.Local.Sample` now generates `Elixir.Mix.Tasks.Local.Sample` instead of `Elixir-Mix-Tasks-Local-Sample`

**Impact:**
- This is a **significant breaking change** for any code that depends on the exact representation of module atoms
- More intuitive and consistent with how modules are written in source code
- Likely improves interoperability with Erlang code
- Updated 58 files across core, tests, and build artifacts

### 3. .iex File Support (New Feature)

**Key Commits:**
- `865608b5de` - Add initial support for .iex files
- `6e8fb6c630` - Merge pull request #1100: Add support for .iex files
- `ed14ce4bc8` - Add --dot-iex command line option to IEx
- `f688899b95` - Add ability to disable loading of .iex
- `5a99fbfdcd` - Add import_file/1 and /2 helpers

**What Changed:**
Users can now create `.iex` configuration files in their home directory or project that will be loaded when starting an IEx session. These files can contain:
- Variable bindings for use in the shell
- Imports and aliases
- Setup code that runs before the shell starts
- Configuration via `IEx.source/1` to chain multiple `.iex` files

**Features Added:**
- Automatic loading from `.iex` or `~/.iex` paths
- `--dot-iex` command line option to override default locations or disable loading
- `IEx.source/1` helper function for sourcing additional `.iex` files within other `.iex` files
- Proper error handling with stack traces and graceful termination on errors

**Impact:**
- Significantly improves IEx development experience
- Enables reproducible shell environments across teams
- Allows developers to set up common imports and utilities once rather than repeatedly in each session

## Breaking Changes

### 1. **Module Atom Representation** (CRITICAL)
The change from `Elixir-Module` to `Elixir.Module` representation is a breaking change for any code that:
- Pattern matches on module atoms directly
- Uses string representations of modules in configuration or serialization
- Relies on the exact form of module atoms from `Module.name/1` or similar introspection

### 2. **Enum.Iterator → Enumerable Protocol Rename**
- Commit `94f9d4e3f6` - Renamed `Enum.Iterator` protocol to `Enumerable`
- This is a direct rename of the protocol, which changes its external API
- Any code implementing the old `Enum.Iterator` protocol must be updated

### 3. **File.iterator and File.biniterator Removal**
- Commit `45485fba59` - Removed `File.iterator/2` and `File.biniterator/2`
- These functions were replaced by the new reducer-based approach
- Users should use equivalent functions in the File module

## Technical Details

### Module Translation

The change from `Elixir-Module` to `Elixir.Module` affects compilation output:
- **Before:** `Elixir-Mix-Tasks-Local-Sample.beam`
- **After:** `Elixir.Mix.Tasks.Local.Sample.beam`

This aligns with Erlang module naming conventions where dots are valid in atom names and represent hierarchical structure more naturally.

### Reducers Pattern

The reducers approach used in the refactoring is a functional programming pattern where:
- Each enumerable collection implements a protocol with a reduce function
- Operations are composed using these reduce functions
- This is more efficient than creating intermediate collections at each step

### .iex File Evaluation

The `.iex` files are evaluated in a specially prepared scope:
- They have access to the same environment IEx.Server will use
- Bindings from the .iex file are preserved in the shell
- Scope changes (imports, aliases) are preserved for the session
