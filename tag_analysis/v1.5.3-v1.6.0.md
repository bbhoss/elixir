### Make split operations consistent with replace

**Author:** José Valim <jose.valim@plataformatec.com.br>
**Date:** 2017-09-12 13:34:45 +0200
**Commit:** afd51e82d5f443e8aba5932ca3f50d13e828fd7d

Both String.replace/3 and Regex.replace/3 consider there is
an empty string before and after the subject when doing replacements:

    String.replace("abc", "", "x")
    #=> "xaxbxcx"

This change makes String.split/2 and Regex.split/2 consistent
with this operation by returning empty strings before and after
the split subject:

    String.split("abc", "")
    #=> ["", "a", "b", "c", ""]

Closes #7023

### Files with only comments are no longer always stale (#7078)

**Author:** jgmchan <jgmchan@gmail.com>
**Date:** 2017-12-06 05:30:15 +1100
**Commit:** 31727805f7280fde27f1d3a107113ead78808ab9

At the beginning of compilation, initial `:source` records of the files that
needs to be compiled are added to an Agent process. These records are then
updated when the files are compiled and then written to the compile manifest.

The `:size` field in the initial record has a default of 0, and since files
without any code (they only have comments or newlines) are not compiled, this
is never updated with the actual size of the file before the compile manifest
is written to disk.

These files are always seen as stale because their size on disk does not match
the compile manifest.

This is fixed by adding the actual size of the file to the initial record.

Closes #7066

**Date:** 2017-07-01 11:45:55 -0700
**Commit:** 6ab811c638b4cfd5c4b6304606c85b9f394a7b55

This makes defining guards easier, since it does the boilerplate
for you and raises at compile time in the defguard macro when
you do something not allowed in guards (as opposed to whenever
the new guard happens to be used as a guard).

passes the implementation through `:elixir_expand.expand/2` in
a guard context, and if nothing is raised, transforms the impl
into a macro that works both inside and outside of guard contexts.

### Optimise Keyword.delete/2 and friends (#6564)

**Author:** Michał Muskała <michal@muskala.eu>
**Date:** 2017-09-15 12:36:46 +0200
**Commit:** d4a3819646f7c8cf62894584503764ce68b74dfc

This optimises all functions similar to Keyword.delete/2:

  * Keyword.delete/2
  * Keyword.delete/3
  * Keyword.delete_first/2

The changes are:

  * use by-hand recursion instead of non-BIF :lists calls
  * in case we end up not deleting a value, use trow-catch to return the
    original list unmodified (this significantly lowers memory use)
  * build the result through body recursion, this way when we unwind the stack
    we free all the data and leave no garbage behind for the GC.

In benchmarks, the new Keyword.delete/2 functions is twice as fast as the old
implementation. Since it's frequently used internally by the Keyword module (for
example in Keyword.put/3) this improves the efficiency of all those functions.

Benchmark reference: https://gist.github.com/michalmuskala/f7f38151495acf7ead131f80271359e7

### Remove incorrect wording regarding test cases

**Author:** José Valim <jose.valim@plataformatec.com.br>
**Date:** 2017-08-24 12:20:09 +0200
**Commit:** 23c7542d95683a497a7b93071b9ccbbeb9e45d2f

Previously, we would use `case` to refer to the whole module
but a `case` is actually a *single test*. We have fixed this
by introducing a new `ExUnit.TestModule` struct and by adding
a new attribute called `:module` to the relevant places.

The changes were kept backwards compatible but we do recommend
developers to:

  * Access the `:module` field instead of `:case` field
  * Replace the `:case_started` and `:case_finished` callbacks
    in their formatters by `:module_started` and `:module_finished`

The previous callbacks will continue to receive `ExUnit.TestCase`
structs but the new callbacks will receive `ExUnit.TestModule`.

Unfortunately those field names and callbacks cannot be deprecated,
so they will be one of the backwards incompatible changes required
for Elixir 2.0.

### Use orelse instead of or when expanding in operator (#6314)

**Author:** Michał Muskała <michal@muskala.eu>
**Date:** 2017-07-16 12:50:21 +0200
**Commit:** 92a3bf76a396988af0acf02fde6aa3c6d85a4d70

orelse may lead to better code in many occasions - Since we're comparing
to literals, there's no semantic difference.

This also means, the compiler is able to figure out more "will always match"
checks. For example in a situation like the following a warning will be emitted.
This pull request also fixes such warnings in the test suite.

    if true do
      IO.puts("true")
    end

One problem with using `orelse` is that it will short-circuit and not evaluate
some side-effecting things, for example:

    1 in [1, send(self(), :foo)]

To remedy this, we'll traverse the right side of `in` and extract any things
that are not simple literals to variables, so that the above example expands
to something like the following:

    var0 = send(seld(), :foo)
    var = 1
    var === 1 or var === var0

This guarantees all side-effects are performed and we still retain benefits of
the short-circuiting comparisons in the end.

### Move away from rata die reference and use iso_days instead (#6328)

**Author:** José Valim <jose.valim@gmail.com>
**Date:** 2017-07-14 14:43:06 +0200
**Commit:** 187c96d57496ea0b58ab9190820d53d5e10d6630

We chose to use the year zero in the astronomical year
numbering as a reference point, as it is also the reference
used by Calendar.ISO, the default calendar used by Elixir,

It is also the same epoch used by Erlang's :calendar module.
Note we chose to not call it gregorian epoch due to the confusion
between January 1 AC 1 and 0000-01-01. The latter actually maps
to January 1 BC 1.

We also moved away from Calendar.Julian, which could have been
based on Calendrical Calculations, and chose Calendar.Holocene,
which adds exactly 10,000 years to Calendar.ISO and as such has
a very straigh-forward implementation.

More information:

  + https://en.wikipedia.org/wiki/Year_zero
  + https://en.wikipedia.org/wiki/Holocene_calendar
