### Changelog: explain `mix test --failed` more accurately. (#7911)

**Author:** Myron Marston <myron.marston@gmail.com>
**Date:** 2018-07-16 00:21:54 -0700
**Commit:** 3dbe8a6661d42fc504584c53ca195ee1575016d4

`mix test --failed` runs all tests that failed the last time they ran,
even if they were not included in the last run of the test suite. This
is important, because it means that you can run individual failed tests
to focus on fixing them without worrying about mix losing track of the
other failed tests.

**Author:** Sihui Huang <sihuih@gmail.com>

### Add hints on mismatched do/end and others pairs

**Author:** José Valim <jose.valim@plataformatec.com.br>
**Date:** 2018-06-10 13:49:50 +0200
**Commit:** 5edb1d2739af074cf555f4300de9da71c214211d

When you are working on large files and you add new code,
you may forget to add a `do` or an `end`. In those cases,
the error message usually points to the first `do` or the
last `end` in the file, which are usually far away from
the source of the error.

This pull request adds a simple heuristic based on the
indentation of the tokens, to try to provide hints of
where the source may be. Those hints are not deterministic
but they may be able to point users to the source of the
problem.

For example, in this case:

    defmodule MyApp do
      def one do
      # end

      def two do
      end
    end

we know that we now that `def two do` is happening on the
same indentation as `def one do`, which may mean that
`def one do` was not closed properly. We store this as a
hint in case the terminators do not match later.

Similarly, in the case below:

    defmodule MyApp do
      def one
      end

      def two do
      end
    end

The `end` on line 3 will end-up closing the defmodule `do`,
on line 1. Because their indentation do not match, it may
be that there is a missing `do`, where the `end` was supposed
to align.

Some basic testing show those heuristics work on the majority
of the cases, but we will only be sure when we have enough
feedback from the community.

### Condititionally compile and lazily compute __STACKTRACE__ (#7648)

**Author:** José Valim <jose.valim@gmail.com>
**Date:** 2018-05-07 15:33:36 +0200
**Commit:** 75541cf47240f0104b91672eb0b1048a9cb44ef4

Erlang/OTP 20 warns if the stacktrace is read outside of a
catch/rescue. This commit mirrors this behaviour by consistently
warning on `System.stacktrace/0` being used outside of a
catch/rescue.

Erlang/OTP 21 warns whenever System.stacktrace/:erlang.get_stacktrace
are used. Therefore we need to promote the usage of `__STACKTRACE__`
and make sure to conditionally compile it according to the OTP version.
This requires changes to the Exception normalization mechanism
so we compute `__STACKTRACE__` only when strictly required.

In future Elixir releases, `System.stacktrace/0` will warn when
used even inside catch/rescue.

### Split Kernel.Typespec into Kernel.Typespec and Code.Typespec (#7462)

**Date:** 2018-03-18 22:45:44 +0100
**Commit:** 4f14aea9f6bf1c8ae5ed1da88b5168424616e11a

logic during compilation, such as definitions, conversion to
Erlang and warnings. Its API shall never be public.

from .beam files and conversion back to Elixir AST. Its API
may be made public in the future but it is currently private.

This PR also simplifies definition of typespecs internally by
avoiding multiple macro passes and speeds up typespec processing
on OTP 20+ by skipping the translation pass from Elixir to Erlang.

The test suite was also reorganized and made async: true.

### Optimize ExUnit manifest building

**Author:** José Valim <jose.valim@plataformatec.com.br>
**Date:** 2018-02-09 10:03:03 +0100
**Commit:** deb2aa50dd40e4c1fbe4cf2a33b6af9054b565f3

  * The most expensive operation was the cost of a missing
    Code.ensure_loaded?/1 call, since it performs a file system
    traversal. For this reason the new implementation simply
    assumes the module has been loaded, because we tried to run
    its tests, otherwise we don't assume anything at all. This
    was particurlaly expensive when running only a subset of the
    suite. This change reduced the time from 3.3s to 120ms.

  * The second most expensive operation was the conversions from
    map to list and vice-versa. Adding tests in a loop also caused
    frequent updates in the map. To solve this, we store the manifest
    as a list, simply prepending entries which is very cheap, and
    convert only the new manifest to a map and only once. The prune
    and merging steps have been unified, reducing the time to 0.6ms.

  * A `new` function has also been added so we can create manifest
    in other files without hardcoding its internal structure. The
    manifest type has been declare as opaque.

the left and right side are shown, except it has been
generalized to arguments:

    foo = {1, 2, 3}
    assert is_list(foo)

will show in error reports as:

    1) test name (Module)
       Expected truthy, got false
       code: assert is_list(foo)
       arguments:

           # 1
           {1, 2, 3}

       stacktrace:
           test/example_test.exs

This behaviour is always enabled, except for macros and
special forms, where rewriting the arguments may change the
macro behaviour.

A function Macro.special_form?/2 has also been added to
support this functionality.
