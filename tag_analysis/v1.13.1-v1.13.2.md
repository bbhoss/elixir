# Changes from v1.13.1 to v1.13.2

## Release Information

- **Release Date**: January 13, 2022
- **Date Range**: December 16, 2021 to January 13, 2022
- **Total Commits**: 13 commits (excluding the release commit itself and CHANGELOG updates)

## Summary

v1.13.2 is a maintenance release that focused on fixing bugs and reversing an API change that proved to be too aggressive. The release contains important compiler fixes, improved tooling warnings, and flexibility enhancements for complex release configurations. A key theme is the recognition that deprecating `map/filter/reject` on Map and Keyword was premature, as these functions were already widely used in projects.

## Major Changes and Themes

### 1. API Change Reversal: Map/Keyword Functions
The most significant change in this release is the **reversal of the deprecation** of `map/filter/reject` functions on `Map` and `Keyword` modules. While these were deprecated in v1.13.0 (commit e61ed47066), this caused issues with existing projects that were already using them. Rather than forcing migration pressure on users, the decision was made to:

- **Restore** the functions to their full functionality
- **Document** when and how to use them appropriately (with guidance on preferring Enum when dealing with collections)
- This demonstrates pragmatic API evolution - acknowledging that a deprecation path that's too aggressive can be reversed if real-world usage patterns justify it

**Relevant Commits:**
- `e61ed47066` - Initial deprecation (Dec 16)
- `d25ce48d5d` - Restoration and documentation improvement (Jan 12)

### 2. Compiler Bug Fixes

#### Nested `uniq:` Accumulator Scope Clash (Commit 01a4889e39)
**Issue**: When using nested comprehensions with the `uniq:` option, variable scope wasn't properly preserved, leading to potential name clashes in the generated code.

**Fix**: Modified the `build_reduce` function to properly return and thread through the state (`S`/`SR`) rather than bundling it with the expression. This ensures each nested level maintains its own scope context.

**Impact**: Users with complex nested comprehensions using `uniq:` would have experienced incorrect behavior or crashes. This fix ensures proper variable scoping in generated code.

**Code pattern affected**:
```elixir
# Now works correctly
for x <- list, uniq: true do
  for y <- nested, uniq: true do
    process(x, y)
  end
end
```

#### Context Modules in Optimized defmodule (Commit 6549b00eba)
**Issue**: When using the optimized `defmodule` compilation path, context modules weren't being properly tracked in the compilation environment.

**Fix**: Modified `elixir_compiler.erl` to preserve and update the `context_modules` list in the environment when compiling modules.

**Impact**: Ensures that `__ENV__.context_modules` correctly reflects the module hierarchy even in optimized compilation paths. This is important for macros that rely on context information.

#### Code Fragment Warnings (Commit 3d3453c1e2)
**Issue**: The `Code.Fragment.container_cursor_to_quoted/2` function was emitting spurious warnings during completion/cursor analysis, which is undesirable for IDE features.

**Fix**: Refactored the warning system to use a `warning_file` parameter instead of a `file` parameter. When `nil` is passed, no warnings are emitted. This allows the fragment parser to run silently for IDE use cases.

**Impact**: IDE integrations and code completion features can now use the fragment parser without triggering compiler warnings, improving the user experience with editor support.

### 3. Compiler Warnings and Validation

#### Protocol Callback Validation (Commit ab1da111bf)
**Issue**: Protocols shouldn't allow zero-arity callback definitions, as they should be defined as regular functions using `def` instead.

**Fix**: Added validation to warn users when zero-arity `@callback` definitions are found in protocols. The fix properly handles callbacks without explicit arity annotations (e.g., `@callback foo :: {:ok, term}`).

**Impact**: Prevents incorrect protocol definitions and guides users toward the proper pattern. The validation uses `List.wrap()` to handle both annotated and non-annotated arities.

**Example warning triggered**:
```
cannot define @callback foo/0 inside protocol, use def/1 to outline your protocol definition
```

### 4. Tool Enhancements

#### Mix Test Coverage Reporting (Commit 66b4ab19ae)
**Feature**: When a test coverage threshold check fails, users now see a clear, formatted message showing:
- The actual coverage percentage achieved
- The required threshold
- A clear indication that the coverage test failed

**Before**: Silently exiting with error code 3

**After**:
```
Coverage test failed, threshold not met:

    Coverage:   62.35%
    Threshold: 100.00%
```

**Impact**: Developers get immediate, clear feedback about why their coverage checks failed, making it easier to diagnose and fix coverage gaps.

#### Formatter Plugin Priority (Commit 071285403d)
**Issue**: The code formatter was checking built-in Elixir formatting rules before checking configured formatter plugins, preventing plugins from handling `.ex` and `.exs` files.

**Fix**: Reordered the formatter detection logic to check plugins first:
```erlang
# Before: Built-in formatters checked first
cond do
  ext in ~w(.ex .exs) ->
    &elixir_format(&1, ...)
  plugin = find_plugin_for_extension(...) ->
    &plugin.format(&1, ...)
end

# After: Plugins checked first
cond do
  plugin = find_plugin_for_extension(...) ->
    &plugin.format(&1, ...)
  ext in ~w(.ex .exs) ->
    &elixir_format(&1, ...)
end
```

**Impact**: Custom formatter plugins can now intercept and format `.ex` and `.exs` files, enabling third-party formatters to extend the system more effectively.

### 5. Deployment and Release Features

#### Release Configuration Flexibility (Commit 280215c24f)
**Feature**: Added `skip_mode_validation_for` option to Mix releases, allowing fine-grained control over application mode validation.

**Background**: Mix.Release enforces strict validation to prevent unsafe application mode combinations (e.g., permanent parent with load-only child). However, complex multi-application systems sometimes need to bypass these checks while maintaining safety for other applications.

**Solution**: New option in release config:
```elixir
releases: [
  app: [
    # Skip validation for these specific apps
    skip_mode_validation_for: [:special_app, :legacy_app]
  ]
]
```

**Impact**: Provides escape hatch for sophisticated applications without completely disabling the safety checks. Users can selectively bypass validation for known-safe scenarios.

### 6. Compatibility Fixes

#### Erlang/OTP Version Compatibility (Commit 4431ac63e2)
**Issue**: Type specifications were using `:erlang.monitor_option()`, which doesn't exist in Erlang/OTP versions before 24.

**Fix**: Defined a local `monitor_option` type that works with current OTP versions:
```elixir
@typep monitor_option ::
         [alias: :explicit_unalias | :demonitor | :reply_demonitor, tag: term()]
```

With a TODO comment to use the native type once OTP 24+ becomes the minimum requirement.

**Impact**: The codebase remains compatible with older Erlang/OTP versions while being ready for the future.

#### Logger CHANGELOG Entry (Commit d5e7446399)
**Documentation**: Added missing CHANGELOG entry for Logger changes in this release.

## Breaking Changes

**None**. In fact, this release *removes* a breaking change by restoring `map/filter/reject` functions that were deprecated in v1.13.0.

## Notable Implementation Details

### Scope Preservation Pattern
The fix for nested `uniq:` comprehensions introduces an important pattern for scope-aware code generation:
```erlang
% Instead of: {Result, S} -> Result
% Use: {Result, NewState} -> properly thread state through all levels
{ReduceExpr, SR} = build_reduce(...),
{?remote(Ann, lists, reverse, [ReduceExpr]), SR}
```

This ensures each nested comprehension maintains its own variable namespace.

### Conditional Warning System
The Code.Fragment fix demonstrates a clean pattern for conditional warnings:
```erlang
warn(LineColumn, Message) ->
  case get(elixir_parser_warning_file) of
    nil -> ok;
    File -> elixir_errors:erl_warn(LineColumn, File, Message)
  end.
```

This allows the same parsing code to work in warning-sensitive contexts (compilation) and warning-suppressed contexts (IDE features).
