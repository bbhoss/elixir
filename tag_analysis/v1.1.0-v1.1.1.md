# Changes from v1.1.0 to v1.1.1

## Release Information

- **Version Range**: v1.1.0 → v1.1.1
- **Release Date**: September 28, 2015
- **Release Window**: September 25 - September 28, 2015
- **Total Commits**: 5 commits (plus release commit)
- **Release Type**: Patch release (v1.1.1 is a bug fix release)

## Summary

Version 1.1.1 is a maintenance release focused on resolving critical bugs discovered in the v1.1.0 release. This patch addresses issues in core data type handling (ranges), testing infrastructure (assertions), application configuration, and type definitions. The release demonstrates the Elixir team's commitment to stability, with particular attention to edge cases in commonly-used features and improved error reporting for developers.

The changes are conservative and targeted, with no breaking changes introduced. This is a recommended upgrade for all users running v1.1.0.

## Bug Fixes

### 1. **Range Integer Type Validation** (Core)
**Commit**: `84b33461f3` | **Author**: José Valim | **Date**: Sep 28, 2015

**Issue**: The `Range.member?/2` function was not properly validating that the value parameter was an integer. This caused inconsistent behavior when checking membership with non-integer values (e.g., floats).

**Fix**: Added a guard clause `when is_integer(value)` to the primary `member?/2` function and a fallback clause that returns `false` for non-integer values. This ensures that `Enum.member?(1..10, 5.0)` correctly returns `false` instead of potentially returning unexpected results.

**Files Modified**:
- `lib/elixir/lib/range.ex` - Added type guard and fallback pattern
- `lib/elixir/lib/enum.ex` - Updated documentation with test case for non-integer behavior
- `lib/elixir/lib/code.ex` - Documentation cleanup

**Impact**: Improves type safety in range operations and prevents subtle bugs where floats might be treated as potential range members.

### 2. **ExUnit Assertion Error Message for Multiple Pinned Variables** (Testing)
**Commit**: `a6723dcbc6` | **Author**: Eric Entin | **Date**: Sep 25, 2015

**Issue**: When using `assert_received` with multiple pinned variables, the error message would include duplicate variable assignments, making debugging confusing.

**Fix**: Modified the `pinned_vars/1` helper to:
- Reverse the pinned variables list for proper ordering
- Remove duplicate variable entries using `uniq_by(&elem(&1, 0))`
- Changed the message construction from string concatenation to binary construction for clarity

This ensures error messages correctly display each unique pinned variable exactly once.

**Files Modified**:
- `lib/ex_unit/lib/ex_unit/assertions.ex` - Enhanced `pinned_vars/1` function
- `lib/ex_unit/test/ex_unit/assertions_test.exs` - Added comprehensive test cases for both identical and unique pinned variables

**Impact**: Significantly improves developer experience when debugging message assertions in concurrent/multi-actor code, especially when pattern matching with multiple pinned variables.

### 3. **App Path Failure Stacktrace Display** (Mix Build Tool)
**Commit**: `e88a1b6738` | **Author**: José Valim | **Date**: Sep 28, 2015

**Issue**: When `app_path/1` or `compile/2` failed in Mix (the build tool), the error didn't display stacktraces properly. Additionally, the logic for handling umbrella projects wasn't correct when checking for compiled artifacts.

**Fix**:
- Changed from `Mix.raise` to direct `raise` statement in one path to ensure stacktraces are included
- Fixed the path detection logic for umbrella projects in the `compile/2` function to check the correct directory based on project type
- Added clarifying comments about the App.Start task's role in protocol consolidation

**Files Modified**:
- `lib/mix/lib/mix/project.ex` - Fixed error reporting and path logic
- `lib/mix/lib/mix/tasks/app.start.ex` - Added documentation comment

**Impact**: Developers building umbrella projects get clearer error messages with full stacktraces when compilation checks fail, improving debugging experience.

### 4. **GenEvent Handler Type Definition Cleanup** (Type Definitions)
**Commit**: `2e4c7abe4d` | **Author**: CrowdHailer | **Date**: Sep 28, 2015

**Issue**: The `GenEvent` handler type specification included an obsolete type option `{pid, reference}` that was no longer valid in the current implementation.

**Fix**: Removed the invalid type option from the `@type handler` definition, leaving only:
- `atom` - Simple module-based handler
- `{atom, term}` - Module with custom state

**Files Modified**:
- `lib/elixir/lib/gen_event.ex` - Updated type documentation

**Impact**: Type documentation now accurately reflects the valid handler formats, preventing confusion for developers integrating with GenEvent.

## Themes and Patterns

The v1.1.0 to v1.1.1 release demonstrates three key themes:

1. **Type Safety & Correctness**: The range integer validation fix addresses edge cases in core data types, ensuring operations fail predictably rather than producing surprising results.

2. **Developer Experience**: Multiple fixes focus on improving error messages and debugging information (assertion error messages, stacktrace display), recognizing that clarity of feedback is crucial for productive development.

3. **Precision & Accuracy**: All fixes correct subtle logic errors or incomplete implementations (umbrella project path handling, type definitions, duplicate variable handling) that would cause problems in edge cases or specific project configurations.

## Breaking Changes

**None**. This is a pure bug fix release with no API changes or behavior modifications that would require code updates by end users.

## Upgrade Recommendation

**Strongly Recommended**: Users running v1.1.0 should upgrade to v1.1.1. This patch release resolves several important bugs affecting:
- Core data type operations (ranges)
- Testing infrastructure (assertion messages)
- Build system reliability (Mix error handling)
- Type accuracy (GenEvent type definitions)

There are no compatibility concerns, and the upgrade path is straightforward.
