# Changes from v1.3.3 to v1.3.4

## Release Information

- **Release Date**: October 9, 2016
- **Date Range**: September 26, 2016 - October 9, 2016
- **Total Commits**: 5 commits (including release commit)
- **Tag Range**: v1.3.3 (Sep 17, 2016) to v1.3.4 (Oct 9, 2016)

## Summary

Version 1.3.4 is a focused patch release containing 4 meaningful commits addressing compiler optimizations, testing infrastructure improvements, and compatibility fixes. This release demonstrates the Elixir team's commitment to stability and incremental refinement in the 1.3.x series. The changes focus on three key areas: improving static analysis compatibility with Dialyzer, enhancing test logging, and optimizing the compiler.

The release period (approximately 3 weeks) was relatively quiet compared to v1.3.3, suggesting this is a maintenance release addressing specific issues discovered in the field. All commits are either bug fixes or performance optimizations with no new user-facing features.

## Major Changes

### 1. Dialyzer Protocol Opaque Type Compatibility

**Commit**: `6e2c29c9d48e0face721f60168d732cfd5845e43` (Oct 4, 2016)
**PR**: #5286
**Impact**: Code quality and tooling compatibility

This change addresses a compatibility issue with Dialyzer's static analysis when protocol functions are called with opaque types. Previously, calling a protocol function with an opaque argument would trigger Dialyzer warnings because the `impl_for/1` function's pattern matching clauses made Dialyzer believe it couldn't handle opaque arguments.

**Technical Details**:
- Added a catch-all clause to the protocol implementation dispatch mechanism that does not destructure its argument
- This allows Dialyzer to infer that the function can handle any argument type, including opaque types
- The implementation relies on Dialyzer's current behavior and includes a comment noting this is a "technical hack"
- Changes affect: `/lib/elixir/lib/protocol.ex`, test fixtures, and related tests

**Why This Matters**:
Users relying on Dialyzer for static analysis would have experienced false positive warnings when using protocols with opaque types (common in libraries providing type safety). This fix improves the developer experience for those using Dialyzer in their projects.

### 2. Error Logger Flushing in ExUnit Capture

**Commit**: `f7b32487c0a375fe3aae43e248d92fea0ef3012e` (Oct 1, 2016)
**PR**: #5280
**Impact**: Test logging reliability

This fix ensures that the error_logger is flushed before capturing logs in ExUnit tests. The change improves the reliability of the `capture_log` functionality by guaranteeing that any pending error messages are processed before the capture begins.

**Technical Details**:
- Modified `/lib/ex_unit/lib/ex_unit/capture_log.ex`
- Added explicit flushing of the error_logger before the capture starts
- Minimal change: 11 insertions in 1 file

**Why This Matters**:
When testing code that generates errors or warnings, tests could occasionally fail or produce inconsistent results if error_logger messages were still pending. This fix ensures deterministic test behavior and more reliable test output.

### 3. Compiler Optimization: Eliminate Redundant Match Patterns

**Commit**: `eedc9bc757364742d52392c10faabe05b815e01f` (Sep 27, 2016)
**Impact**: Compiler performance and generated code efficiency

This is a compiler-level optimization that prevents the generation of unnecessary match statements when pattern matching involves the same variable multiple times.

**Technical Details**:
- Modified `/lib/elixir/src/elixir_clauses.erl` (Erlang file, part of the compiler)
- Changed logic to skip building match structures when the same variable is being matched
- 6 insertions, 6 deletions (pattern replacement rather than net addition)

**Why This Matters**:
This optimization reduces redundant bytecode generation, leading to smaller compiled binaries and potentially faster compilation. The change is internal to the compiler and affects generated code quality without changing language semantics.

### 4. Runtime Callback for Exception Validation

**Commit**: `f053df848fbc5852359d8facffdf328f4b6974fe` (Sep 26, 2016)
**Issue**: #5257
**Impact**: Code organization and maintainability

This change refactors the `raise/1` macro implementation by moving exception validation logic from compile-time macro code to a runtime callback function in `Kernel.Utils`.

**Technical Details**:

**Before**: The macro performed complex pattern matching and validation at compile-time:
- Inline case expressions with generated metadata
- Complex pattern matching for binary, atom, exception structs, and fallback cases
- Manual metadata marking for generated code

**After**: Simple delegation to `Kernel.Utils.raise/1`:
```elixir
quote do
  :erlang.error Kernel.Utils.raise(unquote(msg))
end
```

The validation now happens at runtime via these functions in `Kernel.Utils`:
- `raise(msg)` when `is_binary(msg)` - returns `RuntimeError.exception(msg)`
- `raise(atom)` when `is_atom(atom)` - returns `atom.exception([])`
- `raise(%{__struct__: struct, __exception__: true} = exception)` - returns the exception
- `raise(other)` - returns `ArgumentError` with helpful message

**Changes**:
- `/lib/elixir/lib/kernel.ex`: Simplified macro (26 insertions -> 1 line of business logic)
- `/lib/elixir/lib/kernel/utils.ex`: New runtime validation functions (added 29 lines with docs)

**Why This Matters**:
- **Maintainability**: The validation logic is now in a regular function, easier to understand and modify
- **Compiler Simplicity**: Removes complex compile-time logic from the kernel macro
- **Semantics**: No change in behavior; error messages and exception handling remain identical
- **Code Organization**: Better separation of concerns between macro expansion and validation logic
