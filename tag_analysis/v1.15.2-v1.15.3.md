# Changes from v1.15.2 to v1.15.3

## Overview

**Date Range:** July 3, 2023 - July 15, 2023
**Total Commits:** 11
**Release Date:** July 15, 2023

This patch release contains targeted bug fixes and improvements focused on Mix application loading, IEx remote shell functionality, compiler diagnostics, and CLI experience. It's a maintenance release addressing specific issues discovered after v1.15.2.

---

## Summary & Key Themes

The v1.15.3 release focuses on **three main areas of improvement**:

1. **Mix Application Management** - Fixed critical issues with how Mix handles optional applications and application loading
2. **IEx/CLI Stability** - Resolved issues with remote shells and improved error reporting in the interactive shell
3. **Compiler Correctness** - Fixed tail call optimization behavior and improved diagnostic propagation

The changes are primarily bug fixes with a couple of minor enhancements. No major new features are introduced in this release.

## Bug Fixes

### 1. IEx --remsh Compatibility with Erlang/OTP 25+
**Commit:** 173fc52610 (July 3)
**Issue:** #12746
**Author:** José Valim

**Problem:** The `--remsh` (remote shell) flag was broken on Erlang/OTP 25 and later versions. The code was using `Application.ensure_all_started(:elixir)` followed by `System.wait_until_booted()`, which didn't work correctly with newer Erlang versions.

**Solution:** Simplified to use `:elixir.start_cli()` directly, which provides proper initialization compatible with Erlang/OTP 25+.

**Code Change:**
```erlang
# Before
{:ok, _} = Application.ensure_all_started(:elixir)
System.wait_until_booted()

# After
:elixir.start_cli()
```

**Impact:** Users can now use `iex --remsh` with Erlang/OTP 25 and later versions.

---

### 2. Mix.ensure_application! - Optional Applications Support
**Commit:** b79c5a3b4c (July 12)
**Author:** José Valim

**Problem:** The `Mix.ensure_application!/1` function didn't properly handle optional applications. It would raise an error even when the missing application was listed as optional in a dependent app's specification.

**Solution:** Modified the function to track and consider optional applications in the dependency chain. Now it only raises an error if a missing app is not marked as optional.

**Impact:** Proper support for optional OTP applications, preventing false errors during application loading. Critical for cross-platform Elixir installations where some OTP apps might not be available.

---

### 3. Compiler Tail Call Optimization - Stacktrace Preservation
**Commit:** 3bb0a8379d (July 7)
**Author:** José Valim

**Problem:** The Erlang compiler was tail-call optimizing file-root entries (code at module level), which was causing issues with stacktraces and module definition behavior. The previous workaround (using a noop function) was inadequate.

**Solution:** Moved the optimization decision to the Erlang compiler level in `elixir_compiler.erl`, introducing proper guards to prevent tail-call optimization at file root entries while still allowing it elsewhere. Renamed internal function from `eval_or_compile` to `maybe_fast_compile` to clarify intent.

**Impact:** Correct stacktraces in error messages and proper module behavior during definition. This is an important correctness fix for debugging.

---

### 4. Mix Compilation - Load Path Enablement
**Commit:** 9e177fd592 (July 15)
**Author:** José Valim

**Problem:** During recompilation checks (`__mix_recompile__?`), the load path wasn't being properly enabled, causing false recompilation decisions or incorrect dependency resolution.

**Solution:** Ensured the load path is enabled during the recompilation check in the Elixir compiler.

**Impact:** More accurate incremental compilation, reducing unnecessary recompilation cycles.

---

### 5. Clarified Regex.regex? Upgrade Path
**Commit:** 8422af4a2e (July 12)
**Author:** Thibaut Barrère

**Problem:** Users upgrading to v1.15.x encountered confusion about the deprecated `Regex.regex?/1` function and how to migrate code.

**Solution:** Updated documentation in `regex.ex` and compatibility guide to clarify the upgrade path for users still using this function.

**Impact:** Smoother upgrade experience for existing code using deprecated functionality.

## Removed & Deprecated

### Unsupported --no-deps-loading Flag Removal
**Commit:** 0a3df5068c (July 15)
**Author:** José Valim

Removed the `--no-deps-loading` flag from two Mix tasks:

- `mix loadpaths`

This flag was never properly supported and removing it prevents confusion about its functionality.

**Impact:** Minimal - the flag wasn't functional, so removing it shouldn't affect real-world usage.

**Impact:** Better developer understanding of debugging options.
