# Changes from v1.9.2 to v1.9.3

## Release Overview

- **Release Date**: November 5, 2019
- **Date Range**: August 20, 2019 - November 5, 2019 (approximately 2.5 months)
- **Total Commits**: 7 commits (including the release commit itself)
- **Impacted Areas**: Mix build tool (releases), Kernel sigil documentation, package management security

## Executive Summary

Elixir v1.9.3 is primarily a maintenance and security-focused release that improves the releases feature introduced in v1.9.0. The major theme of this release is **security hardening of package installation** coupled with **refinements to the releases system**. A critical deprecation warning was added for unsafe URL-based package installations, and several enhancements and bug fixes were made to the release building process.

This is a minor patch release that doesn't introduce breaking changes for existing applications, but does deprecate unsafe practices going forward. The release demonstrates a proactive approach to security by warning users about installation methods that will be removed in v1.10.

## Major Features and Improvements

### 1. Tarball Generation for Releases (Enhancement)

**Commit**: `b6ea714339` | **Author**: Gary Rennie | **Date**: August 20, 2019

The most significant feature addition in this release is the ability to automatically create compressed tarballs of releases. This is particularly valuable for deployment scenarios.

**What Changed**:
- Added `:tar` as a valid step in the release build pipeline
- The tarball is created with the naming convention `RELEASE_NAME-RELEASE_VERSION.tar.gz`
- Can be placed in the release pipeline either before or after `:assemble`, though tarballs can only be created from an assembled release
- Tarballs use gzip compression and Erlang tar format for maximum compatibility
- Includes proper validation to ensure `:tar` step can only appear once and must come after `:assemble`

**Impact**: Simplifies deployment workflows by eliminating the need for custom scripts or tools to create release tarballs. Users can now directly generate production-ready artifacts from the `mix release` command.

**Code Changes**: Modified `Mix.Release` struct documentation and `Mix.Tasks.Release` to add the `make_tar/1` function that leverages Erlang's `:erl_tar` module.

### 2. Improved Release Configuration (Bug Fix)

**Commit**: `96c9500afd` | **Author**: Chris de Graaf | **Date**: June 24, 2019

**What Changed**:
- Fixed the behavior of `default_release` option in release configuration
- When building a release without explicitly specifying which named release to build, the system now correctly falls back to the configured `default_release` option
- Ensures that projects with multiple named releases can designate a primary release for convenience

**Impact**: Enables better multi-release projects where developers can configure a preferred release to be built by default, reducing the need to explicitly specify which release to build in common development and CI scenarios.

**Code Changes**: Modified `Mix.Release` module to properly check and utilize the `default_release` configuration option when the release name is not provided.

### 3. Deterministic Release Boot Scripts (Bug Fix)

**Commit**: `215229c28f` | **Author**: Michał Kalbarczyk | **Date**: November 3, 2019

**What Changed**:
- Fixed non-deterministic ordering in generated release boot scripts
- Ensures that boot scripts contain the same content regardless of how many times they're generated or in what order dependencies are processed
- Critical for reproducible builds and release artifact consistency

**Impact**: Enables reproducible, bit-for-bit identical releases across different build machines and runs. This is essential for:
- Verification and auditing of production deployments
- Ensuring all environments receive identical binaries
- Version control of release artifacts (if needed)
- Supply chain security and artifact signing

**Code Changes**: Modified the boot script generation logic in `Mix.Release` to sort dependencies deterministically before generating scripts.

## Deprecations and Security Improvements

### Critical: Unsafe URL-Based Package Installation Deprecation

**Commit**: `fad48c401f` | **Author**: Bram Verburg | **Date**: February 5, 2018 (backport)

This is the most significant change from a security perspective, though the commit date indicates this was backported from an older development branch.

**What's Being Deprecated**:
- Using URLs directly with `mix archive.install`
- Using URLs directly with `mix escript.install`
- Using URLs directly with `mix local.rebar`

**What Changed**:
- Added warnings when users attempt to use URLs with these commands
- These will become hard errors in Elixir v1.10
- Full removal of URL support scheduled for v1.10

**Why This Matters**:
- Direct URL installations can be vulnerable to man-in-the-middle attacks
- No verification mechanism is in place for URL-based downloads
- Encourages users to adopt safer installation methods

**Recommended Migration Path**:
Instead of:
```bash
mix archive.install https://example.org/installer.ez
```

Users should:
1. Download the artifact manually using trusted tools:
   ```bash
   wget https://example.org/installer.ez
   mix archive.install installer.ez
   ```

2. Or better yet, use Hex-based installation (if available):
   ```bash
   mix archive.install hex phx_new
   ```

**Code Changes**: Added utility functions to `Mix.Utils` for URL validation and warnings. Modified installation tasks for archives, escripts, and rebar to check for URLs and emit deprecation warnings. Updated tests to verify warning behavior.

### Related Fix: Rebar3 Installation Warning Cleanup

**Commit**: `34dc2466e4` | **Author**: José Valim | **Date**: November 5, 2019

**What Changed**:
- Removed extraneous warnings when performing "safe" rebar3 installations
- Specifically cleaned up messaging in the `mix local.rebar` task to not show unnecessary warnings for file-based installations (only URL-based ones)

**Impact**: Improves user experience by reducing noise in the build output while still warning about unsafe practices.

## Breaking Changes

**None**. This is a fully backward-compatible patch release. The deprecation warnings for URL-based installations are advisory in nature—existing code will continue to function but will emit warnings to encourage migration.

## Notable Implementation Details

### Release Tarball Implementation
- Uses Erlang's native `:erl_tar` module for compatibility
- Applies gzip compression for efficient storage
- Properly handles symbolic links with `:dereference` option
- Excludes unnecessary directories (like ignored apps and directories)
- Follows a clean file structure in the tarball

### Security Warning System
- Implements centralized URL detection in `Mix.Utils`
- Consistent warning messaging across three different installation commands
- Clear guidance for users on alternative safe installation methods

## Version Context

This release comes 3 months after the major v1.9.0 release that introduced the releases feature. The progression shows the Elixir team quickly addressing:
1. User feedback and enhancement requests (tarball generation)
2. Bug reports and edge cases (deterministic builds, default release selection)
3. Security concerns identified by the community (URL installation safety)

## Recommended Actions for Users

1. **Update immediately** if using v1.9.0, v1.9.1, or v1.9.2 and any of these apply:
   - You're using releases in production
   - You rely on release artifacts for deployment
   - You use archive or escript installations

2. **For package maintainers**:
   - Stop providing URL-based installation instructions
   - Migrate to Hex-based installation or direct file-based downloads
   - Update documentation before v1.10

3. **For release users**:
   - Consider enabling tarball generation if deploying releases to container or cloud environments
   - Enable deterministic builds for supply chain verification

## Summary

Elixir v1.9.3 represents a polished iteration on the v1.9 release series, focusing on practical improvements to the releases feature and addressing security concerns around package installation. While not introducing groundbreaking new features, it demonstrates the Elixir team's commitment to:
- Developer convenience (tarball generation)
- Build reproducibility (deterministic boot scripts)
- Security best practices (URL installation deprecation)
- Release quality (bug fixes for edge cases)

The release is a recommended update for all Elixir v1.9 users, particularly those using the releases feature or managing package installations.
