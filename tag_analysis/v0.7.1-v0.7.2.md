# Changes from v0.7.1 to v0.7.2

## Release Information

- **Release Date:** December 4, 2012
- **Date Range:** November 18, 2012 to December 4, 2012 (16 days)
- **Total Commits:** 135 commits
- **Contributors:** José Valim (primary), Yurii Rashkovskii, and community contributors

## Summary

Version 0.7.2 represents a significant step forward for Elixir with major improvements in three critical areas: record compilation optimization, type specification syntax refinement, and interactive development experience. This release demonstrates the project's maturing focus on developer ergonomics, performance optimization, and creating a more robust type system for static analysis. The changes reflect Elixir's commitment to balancing practical development needs with the foundation for more powerful tooling.

The release emphasizes:
1. **Smart Compilation Optimizations** through the Record Rewriter feature that intelligently optimizes record access patterns
2. **Type System Evolution** with a redesigned function type specification syntax that's more expressive and intuitive
3. **Enhanced REPL Experience** with improved helper functions and startup performance in IEx
4. **Standard Library Refinements** with better string utilities, sorting performance, and API consistency

## Major Features and Improvements

### 1. Record Rewriter (Compilation Optimization)

The introduction of the Record Rewriter is one of the most significant features in this release. This is a compile-time optimization that intelligently rewrites record access patterns into more efficient tuple operations.

**Key Commits:**
- `0f1584c0fa` - Initial work on RecordRewriter
- `d4c243652` - Extend reach of record rewriting
- `498ac849f` - Record rewriting works with case clauses
- `088ef2fbe8` - Support try/receive in record rewriter
- `82cf622e9b` - Enable record rewriter inference
- `c7f67bc52a` - Rewrite records accessors when possible
- `a629fdac0d` - Document the record access rewrite feature

**What Changed:**
The Record Rewriter analyzes code at compile time and rewrites inefficient record access patterns to optimized tuple operations. This includes:
- Automatic conversion of record field access to tuple operations when possible
- Support for complex patterns like case statements, try/rescue blocks, and receive expressions
- Smart inference that avoids rewriting when it could cause conflicts
- Proper handling of update operations (`update_*` fields)
- Validation to ensure the rewriter is a no-op for non-record fields

**Impact:** This optimization reduces runtime overhead of record operations, making them much faster without requiring changes to user code. It represents Elixir's pragmatic approach to performance.

### 2. Type Specification Syntax Redesign

A major overhaul of how function type specifications are expressed, making them more readable and intuitive.

**Key Commits:**
- `0db1f72` - Change function type specification syntax (WIP)
- `e112850` - More work on improved typespec syntax
- `ced5a43` - Support -> inside parenthesis
- `f249eab` - Ensure parenthesis are allowed in call args
- `b1cb680` - Change fun(... :: signature) specification format to (... -> signature)
- `f0ab87f` - Add a more explicit syntax for ((...) -> ...): (fun(...) -> ...)
- `3eb509f` - Support -> in Macro.to_binary and improve fn printing too
- `bc53005` - Add new typespec syntax to defcallback too
- `71de5f0` - Merge branch 'jv-new-spec'

**What Changed:**
The old function type syntax `fun(... :: signature)` has been replaced with a more intuitive arrow-based syntax `(... -> signature)`. This makes function signatures more readable and aligns better with pattern matching and pattern description conventions in Elixir.

Example transformation:
- Old: `@spec my_func :: (integer, integer -> integer)`
- New: `@spec my_func :: ((integer, integer) -> integer)`

**Impact:** More readable and intuitive function type specifications that developers understand at a glance. This is part of building towards a mature type system for future tooling.

### 4. String Module Enhancements

**New String Utilities:**
- `5c29d76` - Add String.Unicode.{lstrip,rstrip}
- `2984771` - Add String.strip/1

- `875d100` - Strip whitespace characters instead of space in String.rstrip
- `4227d94` - Support `\xXX` and `\x{HEX}` escape sequences in strings and char lists

**What Changed:**
- New `String.strip/1` function for removing leading and trailing whitespace
- `String.Unicode.lstrip/1` and `String.Unicode.rstrip/1` provide Unicode-aware whitespace stripping

- The strip functions properly handle all Unicode whitespace categories, not just ASCII spaces

**Impact:** Better handling of string data, especially important for applications dealing with international text and proper whitespace handling.

### 5. Enum and List Performance Improvements

Significant performance work and API rationalization in collection handling.

**Key Changes:**
- `5c967ac` - Add Enum.sort which uses merge sort (considerably faster than Enum.qsort)
- `600c802` - Deprecated `Enum.qsort` and `List.sort` in favor of `Enum.sort`
- `36ceb48` - Performance improvements to Enum.drop/take
- `362ff69` - Move more behaviour to Enum

**What Changed:**
A new `Enum.sort/1` using merge sort algorithm replaces the quicksort-based `Enum.qsort`. Merge sort provides better consistency and performance characteristics. The old functions are deprecated. Performance optimizations to `Enum.drop/take` make collection manipulation faster.

**Impact:** Better performance for common operations and a more unified, simpler API for developers.

## Breaking Changes and Deprecations

### Deprecations (Will be removed in future versions)

1. **Record Default-based Functions**
   - Commit: `9b3d851`
   - Deprecate the old `defaults(field: value)` syntax for generating functions with default values
   - Impact: Record APIs will become cleaner and more explicit

2. **Enum.qsort and List.sort**
   - Commit: `600c802`
   - These functions are deprecated in favor of the new `Enum.sort` using merge sort
   - Old code will still work but should be updated

3. **ExUnit assert syntax**
   - Commit: `3de6776`
   - `assert left in right` is deprecated in favor of `assert left inlist right`
   - Impact: More explicit and readable assertion syntax

### Removals

1. **IEx.preload module removed**
   - Commit: `8df8034`
   - The preload mechanism was simplified as part of improving IEx startup

2. **Previously deprecated code removed**
   - Commit: `2016b4b`
   - Various APIs deprecated in earlier versions are now fully removed

## Upgrade Path

### For Most Users
This release is largely backward compatible. Most code written for v0.7.1 will continue to work in v0.7.2 without modification.

### Required Changes
- Code using `Enum.qsort` or `List.sort` should migrate to `Enum.sort`
- Code using `assert left in right` in ExUnit should update to `assert left inlist right`
- If using the old record default-based function generation, consider migrating away from deprecated APIs

### Recommended Changes
- Take advantage of the new `(... -> signature)` typespec syntax for better readability
- Use the enhanced IEx helpers for better interactive development
- Leverage the new String utilities for better Unicode support

## Conclusion

Elixir v0.7.2 represents a maturation of the language with a focus on practical performance optimizations, better developer tooling, and a more refined type system foundation. The Record Rewriter shows the project's commitment to zero-cost abstractions, while the typespec syntax redesign and IEx improvements demonstrate a focus on making Elixir more accessible and powerful for real-world development. The release maintains backward compatibility while introducing features that will serve as building blocks for future development tools and optimizations.
