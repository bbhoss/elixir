# Changes from v1.7.0 to v1.7.1

## Release Information
- **From:** v1.7.0 (July 25, 2018)
- **To:** v1.7.1 (July 26, 2018)
- **Duration:** 1 day
- **Total Commits:** 3 feature/fix commits + 1 release commit = 4 total

## Summary

Version 1.7.1 is a patch release that primarily addresses performance optimizations and critical bug fixes in the Calendar module. This release was expedited (released just one day after v1.7.0), indicating it addressed urgent issues discovered immediately after the v1.7.0 release.

The release focuses on three key areas:
1. **DateTime/NaiveDateTime Performance Improvements** - Optimized ISO-8601 parsing to reduce allocations and improve parsing speed
2. **Code Structure Refactoring** - Refactored internal parsing logic to resolve Dialyzer type-checking issues
3. **Dialyzer Infinite Loop Fix** - Resolved critical static analysis issues that were causing Dialyzer to hang

## Major Changes & Improvements

### 1. ISO-8601 UTC Parsing Optimization
**Commit:** `9752f1ce05` (July 25, 2018)
**Author:** David Cuddeback

Added a fast-path optimization for UTC timezone parsing in `DateTime.from_iso8601/2`. When parsing an ISO-8601 string with UTC offset (offset == 0), the code now directly constructs the DateTime struct instead of using intermediate transformations. This optimization:

- Reduces unnecessary struct creation and conversion steps
- Provides a specialized code path for the common case of UTC timestamps
- Improves performance for high-frequency ISO-8601 parsing operations
- Sets explicit UTC zone information (`zone_abbr: "UTC"`, `time_zone: "Etc/UTC"`)

**Impact:** Measurable performance improvement for datetime parsing, particularly beneficial for applications heavily using ISO-8601 timestamps.

### 2. NaiveDateTime Intermediate Part Elimination
**Commit:** `89e3a81adc` (July 25, 2018)
**Author:** David Cuddeback

Refactored `NaiveDateTime.new/8` to skip intermediate struct allocations in the Date and Time modules. The original implementation was:
```elixir
def new(year, month, day, hour, minute, second, microsecond, calendar) do
  with {:ok, date} <- Date.new(year, month, day, calendar),
       {:ok, time} <- Time.new(hour, minute, second, microsecond, calendar),
       do: new(date, time)
end
```

The optimized version:
- Inlines validation logic directly in the function
- Eliminates intermediate Date and Time struct allocations
- Creates only the final NaiveDateTime struct
- Adds support for integer microsecond shorthand (converts to `{microsecond, 6}` tuple)

**Implementation Details:**
- Validates the date using `calendar.valid_date?/3`
- Validates the time using `calendar.valid_time?/4`
- Uses a conditional expression to construct the NaiveDateTime directly
- Returns the same `{:ok, naive_datetime}` or error tuples

**Impact:** Reduced memory allocations and improved performance for NaiveDateTime creation, which is frequently used in date/time operations.

## Bug Fixes

### Critical: Dialyzer Infinite Loop in Calendar Module
**Commit:** `07c276ab5c` (July 26, 2018)
**Authors:** Michał Muskała, José Valim
**Issue:** #7993

This was a critical fix addressing Dialyzer infinite loop issues in Calendar module functions. The problem stemmed from guard clauses in pattern matching that made Dialyzer's type inference unstable. Changes were made across four modules:

#### Date Module Changes
- **File:** `lib/elixir/lib/calendar/date.ex`
- **Refactoring:** Extracted pattern matching logic into a private `raw_from_iso8601/2` function
- **Before:** Used guard clauses directly in pattern matching: `def from_iso8601(unquote(match_date), calendar) when unquote(guard_date)`
- **After:** Separated matching and guard evaluation:
  ```elixir
  def from_iso8601(<<?-, rest::binary>>, calendar) do
    with {:ok, %{year: year} = date} <- raw_from_iso8601(rest, calendar) do
      {:ok, %{date | year: -year}}
    end
  end

  defp raw_from_iso8601(string, calendar) do
    with <<unquote(match_date)>> <- string,
         true <- unquote(guard_date),
         # ... rest of validation
  end
  ```
- **Benefit:** Simplified control flow for Dialyzer's type analysis

#### DateTime Module Changes
- **File:** `lib/elixir/lib/calendar/datetime.ex`
- **Key Change:** Separated pattern matching and guards in `from_iso8601/2`
- **Before:** `with <<unquote(match_date), sep, unquote(match_time), rest::binary>> when unquote(guard_date) and sep in @sep and unquote(guard_time) <- string`
- **After:** Split into separate matching and guard assertion steps
- **Reason:** Prevents Dialyzer from creating circular type inference loops

#### NaiveDateTime Module Changes
- **File:** `lib/elixir/lib/calendar/naive_datetime.ex`
- **Pattern:** Similar refactoring as Date module - extracted `raw_from_iso8601/2` private function
- **Scope:** Affected ISO-8601 parsing in the `from_iso8601/2` function

#### Time Module Changes
- **File:** `lib/elixir/lib/calendar/time.ex`
- **Refactoring:**
  - Extracted private `raw_from_iso8601/2` function
  - Simplified public clauses to handle prefix patterns (`?T` prefix for ISO-8601 time format)
  - Moved complex guard logic to private function
- **Before:** Used pattern matching with inline guards and conditional checks
- **After:** Cleaner public API with delegated parsing logic

**Root Cause:** Dialyzer's type inference system was having difficulty with the deeply nested guard clauses and pattern matching combinations, causing infinite loops during static analysis.

**Solution:** By extracting the complex pattern matching and guards into private helper functions, the type inference becomes tractable and more understandable to Dialyzer.

**Impact:**
- Resolves tooling issues preventing Dialyzer from analyzing v1.7.0 code
- Makes the Calendar module compatible with static analysis tools
- No functional changes to behavior, only restructuring for better type analysis
