# Changes from v1.12.2 to v1.12.3

## Release Overview

- **Release Date**: September 5, 2021
- **Date Range**: July 1, 2021 - September 5, 2021 (2+ months)
- **Total Commits**: 13 changes (plus release commit)
- **Primary Theme**: Maintenance release focused on backwards compatibility fixes and build system stabilization

## Summary

Version 1.12.3 is a patch release that primarily addresses backwards compatibility issues introduced in v1.12.2, particularly around Range/Date.Range API changes. The release also includes important stability improvements to the build system and bug fixes for edge cases in compilation and code analysis. This is a conservative, stability-focused release rather than one introducing new features.

The release demonstrates a pattern of careful API management, with the Elixir team reverting problematic changes and ensuring existing code continues to work while maintaining the intended improvements.

## Major Themes

### 1. Backwards Compatibility (Primary Focus)

The dominant theme in this release is restoring backwards compatibility with existing code. Multiple commits specifically address breaking changes, suggesting v1.12.2 introduced some API changes that impacted users.

**Key Issues Addressed:**
- **Range API Changes**: Two separate commits (#11110, #11117) fix backwards compatibility with Range and Date.Range. These were likely breaking changes related to range handling that needed careful restoration while maintaining the benefits of v1.12.2's improvements.
- **Documentation of Breakage**: Commit edb5e7e052 documents a backwards incompatible change (closes #11105), suggesting the team was explicit about known breaking changes that couldn't be easily reversed.

This focus indicates v1.12.2 may have been more aggressive with API changes than expected, prompting this maintenance release to smooth the transition.

### 2. Build System & Incremental Compilation

Several commits target the reliability and efficiency of Elixir's compilation system:

- **Rely on modification time and hash to determine modified sources** (#11080, commit 74f9a299ea): This is a significant improvement to how the compiler tracks changes. Instead of relying on a single signal (mtime OR hash), the system now uses both to ensure accuracy. This is more robust against edge cases where file timestamps might be misleading.

- **Revert content tracking instead of mtime** (commit e00cbe16cd, Aug 24): A high-priority revert suggesting the initial approach to modification tracking had issues. The revert happened late in the cycle (3 weeks before release), indicating this was a critical fix discovered during testing.

- **Purge v8 manifests properly** (commit 5189b292ac): Cleanup of old manifest files ensures the build system doesn't get confused by outdated metadata, important for long-running projects with many rebuild cycles.

- **Make sure .beam files still exist for restored files** (#11187, commit 9df7a548ed): Ensures consistency between source files and compiled .beam files during restoration/recovery operations.

### 3. Compiler & Code Analysis Bug Fixes

- **Do not return context tuples on optimized eval** (commit 9137fd1cb2): Fixes an issue where context information was being returned when it shouldn't be, likely affecting tools that perform code introspection and debugging.

- **Do not crash when handling ambiguity errors** (#11111, commit 616e0d8ccc): Prevents compiler crashes on ambiguous code references, making error handling more robust.

- **Do not error autocompletion with module attribute** (#11120, commit 2ce9d25552): Fixes autocompletion in editors/tools when module attributes are used, improving the development experience with IDEs.

- **Fix regex** (commits 010efd8ec6, c0174044bc): Two separate regex fixes suggest parsing improvements, likely related to code pattern matching in the compiler.

## Notable Changes

### API Consistency: exit_code → exit_status

**Commit**: b558142819 (July 15, 2021)

Renamed `exit_code` to `exit_status` for naming consistency. This is a minor API change that standardizes terminology across the codebase. The change suggests this naming inconsistency was discovered as part of the v1.12.x stabilization efforts.

## Breaking Changes

1. **Range API Changes**: Both commits #11110 and #11117 are explicitly about "keeping backwards compatibility," suggesting v1.12.2 introduced breaking changes to Range handling that had to be carefully restored in v1.12.3.

2. **exit_code → exit_status Rename**: Rename of `exit_code` to `exit_status` in the public API. This is a breaking change for code directly referencing `exit_code`.

3. **Backwards Incompatible Change (#11105)**: One documented breaking change that couldn't be reversed, requiring explicit documentation for users to understand the transition.

## Technical Insights

### Compilation Tracking Complexity

The multiple commits around modification time tracking (mtime/hash) reveal the complexity of incremental compilation. The Elixir team invested in a more sophisticated approach using both modification time AND content hash, then had to revert part of this work. This suggests:

- Initial implementation had performance or correctness issues
- Relying solely on mtime proved insufficient for all cases
- The hybrid approach (mtime + hash) provides better accuracy

### Quality Assurance Patterns

The timing of the revert (August 24, just 12 days before release on September 5) suggests active testing and QA during the stabilization period. Critical issues discovered late in the cycle were addressed quickly.

### Version Migration Focus

The release heavily emphasizes backwards compatibility, indicating the Elixir team's commitment to smooth version transitions. Rather than forcing users to immediately adapt to v1.12.2 changes, they provided v1.12.3 as a stabilization point.

## Conclusion

Version 1.12.3 represents a carefully balanced maintenance release that prioritizes stability and backwards compatibility while addressing critical bugs and improving the build system's reliability. The focus on reverting aggressive changes and restoring API compatibility suggests that v1.12.2 may have been too disruptive, and v1.12.3 serves as a stabilization point for users still adapting to the v1.12.x changes.
